# Prolog — 작가 곁의 조용한 편집자

정유진 선생님의 랜딩 피드백을 굵은 제목과 간결한 집필 언어로 적용한다. 별도로 보관한 브루탈리즘 시안과 독립적인 작업이다.

종이색·명조 제목·필기 영상으로 구성했던 첫 시안은 일반적인 AI 생성 디자인처럼 느껴진다는 평가를 받았다. 웹 사례를 조사한 뒤, 사용자의 진행 요청에 따라 첫 화면을 다시 구현했다. 원고와 인물 기록을 나란히 놓았던 후속 시안도 정보가 과하다는 평가를 받아, 인물 패널과 안내를 제거했다. 이후 서비스와 무관한 소설 발췌도 제거해, 첫 화면의 전경에는 제목과 시작 버튼만 남겼다. 이후 사용자가 제안한 책 본문 백드롭을 추가했다. 본문은 옅은 시각적 배경으로 쓰고, 일부 단어에 인물·장소 강조와 설정 검토 밑줄을 넣어 서비스 기능을 암시한다. 아래쪽 소개 섹션은 기존 구성을 유지한다.

## 2026-11 랜딩 재설계

사용자 요청에 따라 랜딩의 레이아웃과 디자인을 새로 만들었다. 구성은 네 섹션이다.

1. **문구** — “이야기는 길고, 기억은 짧으니까.”와 시작 버튼, 펼친 원고지 펜화.
2. **쓰기 전의 문제점** — 흩어진 설정, 바뀌는 사실, 달라지는 인물, 엇갈리는 원고 파일. 예시는 데모 작품 「붉은 문 너머」(`src/api/mock/demo.ts`)의 실제 어긋남(북쪽 승강장 폐쇄 1998↔2001, 민아 열일곱↔열아홉)을 쓴다.
3. **기능 정리** — 사이드바 메뉴와 같은 이름의 번호 탭 여섯 개(원고, 원고에 물어보기, 등장인물, 세계관, 작품 살펴보기, 팀원 초대)와, 탭마다 실제 앱 화면이 짧게 움직이는 창. 펜 스케치가 아니라 앱 화면 그대로를 보여 준다.
4. **Footer** — 마감 권유, 펜선, 사이트 정보.

이전의 본문 백드롭, 단어 리빌, 필기·대화·타자기 영상과 프레임 시퀀스(`public/landing`)는 제거했다.

### 문구 다듬기 (2026-11-09)

랜딩 문구를 실제 기능에 맞춰 다시 쓰고(txt·docx 업로드, 편집 이력, 근거 장·문장 인용, 인물 네 갈래 추출, 규칙 후보 → 설정 검사 기준, 장 슬라이더·미회수 복선, 편집자/보기 전용 초대 링크) im-not-ai(`humanize-korean`)로 AI 티를 걷어 냈다. 인물 관계와 복선은 작가가 기록하는 기능이라 “자동으로 찾아 준다”고 쓰지 않는다.

### 레퍼런스

- [Notion의 원조 브랜드 일러스트](https://www.notion.com/blog/the-thinking-behind-our-latest-brand-campaign)(Roman Muradov): 흑백 잉크 손그림만으로 정체성을 만든다. → 색은 서비스 토큰만, 그림은 먹선 하나로.
- 문제→해결 서사의 SaaS 랜딩: 문제는 짧게 2인칭으로 공감하고, 기능은 뒤에서 풀어 준다.
- 아래 조사의 워크룸 프레스·Are.na: 시각 중심은 화면당 하나, 실제 원고와 기능이 주인공.
- [유니브 AI](https://univai.co.kr): 기능을 `01 … 05` 번호 탭으로 나열하고, 활성 탭의 진행 막대와 함께 실제 앱 화면을 루프로 재생한다. → 기능 섹션의 탭·진행 막대·실제 화면 구성.

### 펜화 원칙

- 그림은 모두 [roughjs](https://roughjs.com/)로 직접 그린 SVG 펜선이다. 외부 사진·영상·스톡 일러스트는 쓰지 않는다.
- 선은 화면에 들어올 때 차례로 그려지고, 그림 속 글은 차례로 나타난다. 모션 감소 설정이면 완성된 그림을 바로 보인다.
- 음영은 해칭으로 표현한다. 그림 속 글만 손글씨체 카페24 빛나는별(`public/fonts/Cafe24Shiningstar-v2.0.woff2`, `--lp-hand`)을 쓰고 제목·본문·버튼·앱 화면 데모는 Pretendard를 유지한다. 같은 크기에서 더 작게 보여 `--lp-hand-scale`로 키워 쓴다.
- 문제점 그림(`replay`)은 위로 스크롤해 화면 아래로 빠져나가면 그린 순서를 거꾸로 되감고, 다시 내려오면 처음부터 그린다. 아래로 지나칠 때는 그린 상태를 둔다.
- 첫 그림은 누구나 아는 「신데렐라」 12장을 예시로 쓴다. 포스트잇은 옛날 셀 애니메이션처럼 몇 가지 자세를 뚝뚝 끊어(`steps`) 오가며 날리고, 원고지도 그 1/4 폭으로 더 느리게 날린다. 만년필은 첫 화면이 뜨자마자(0.75초) 포스트잇 아래쪽을 따라 움직이며 “12장 · 구두 주움”을 적은 뒤 들린다. 글은 펜촉이 지나간 만큼만 드러난다.
- 도구 섹션은 화면을 고정(`sticky`)한 채 세로 스크롤을 가로 이동으로 바꿔 기능을 하나씩 넘기고, 마지막 기능 뒤에 고정이 풀려 아래로 이어진다. 모션 감소 설정이면 고정 없이 위아래로 쌓는다.
- 성능: SVG 필터(`feTurbulence` 등)는 쓰지 않는다. 그리기는 `pathLength=1` + `stroke-dashoffset` CSS transition으로 하고, React는 그림마다 `data-on` 하나만 바꾼다. 경로마다 JS 애니메이션을 걸지 않는다.
- 색은 `tokens.css`의 흰 종이·먹색·보조 회색·회녹색 상호작용색, 그리고 인물·설정·검토 하이라이트를 형광펜 농도로 섞은 값(`--lp-wash-*`)만 쓴다. 하이라이트는 실제 의미(인물·설정·검토)에만 칠한다.
- 섹션 구분은 앱과 같은 2px 먹색 룰, 카드 상자는 쓰지 않는다.

### 기능 섹션의 앱 화면

- 영상·GIF가 아니라 코드로 재현한 화면이다. 앱의 클래스(`.app`, `.sidebar`, `.panel`, `.answer`…)와 순수 컴포넌트(`AnswerCard`, `Stepper`, `RelationshipGraph` + `relationshipView`)를 그대로 쓰고, 데이터는 데모 작품 상수(`src/api/mock/demo.ts`)를 쓴다. 앱 화면이 바뀌면 데모도 함께 바뀐다.
- 화면은 1320px 너비 iframe 안에 그린 뒤 칸 너비에 맞춰 줄인다. 앱 CSS의 너비 규칙(@media)이 데스크톱 기준으로 계산되도록 하기 위해서다. iframe에는 앱 스타일시트를 복사해 넣는다.
- 화면에 보일 때만 재생하고, 한 장면(약 10초)이 끝나면 다음 탭으로 넘어간다. 활성 데모 하나만 그린다. 모션 감소면 마지막 장면에서 멈춘다.
- 창 한 장에 들어오도록 줄인 곳: 원고에 물어보기의 대화 칸 높이와 설명 한 줄, 설정 규칙의 설명 한 줄과 안내 문구, 팀원 초대의 보낸 초대 위치(멤버 표 아래).

구현: `src/features/landing/components/ink/`(생성기·그리기 컴포넌트), `illustrations/`(장면별 펜화), `demo/`(앱 화면 데모와 창 틀), `sections/`(Statement·Problems·Features·Footer). 문구는 `src/content/voice.ts`.

## 서비스의 약속

**당신의 다음 문장을 위해.**

작가는 이야기를 쓰고, Prolog는 그 곁에서 원고와 인물, 세계관을 함께 살핀다. 도구가 작가를 앞서거나 창작을 대신한다고 말하지 않는다.

## 문장의 원칙

- 제목에는 문학적 여운을, 설명에는 실제로 할 수 있는 일을 담는다.
- 기능 설명은 가급적 한두 문장. 장식 라벨이나 같은 뜻의 설명을 덧붙이지 않는다.
- “생성합니다”, “자동 구조화” 대신 “초안으로 정리해요”처럼 작가의 언어를 사용한다.
- AI 제안에는 작가의 검토와 선택을 남긴다. 완벽한 감지, 창작 대행, 실시간 공동 편집을 약속하지 않는다.
- 오류와 저장·삭제·권한은 구체적으로 쓴다. 문학적인 비유로 결과를 흐리지 않는다.
- 비어 있는 서재에는 “새 작품을 만들고 첫 문장을 적어 보세요.”처럼 다음 행동을 안내한다.
- 로그인·회원가입 버튼과 입력 이름은 명확하게 유지한다. 제목에서만 친근하게 맞이한다.

## 시각 원칙 (2026-10 첫 화면, 이번 재설계로 대체)

- 첫 화면의 전경에는 제목과 시작 버튼만 배치한다.
- 제목과 시작 버튼을 하나의 왼쪽 정렬 축에 놓는다.
- 인물 패널, 탭, 필드 설명, 원고 제목, 예시 라벨, 사용 안내, 장식 화살표는 제거한다.
- 별도의 소설 인용문을 전경에 넣지 않는다. 사용자가 요청한 본문 백드롭은 글자 불투명도 9%의 Pretendard 조판으로 표현하고, 모바일에서는 8%로 낮춘다.
- 본문 백드롭은 데스크톱에서 두 단, 모바일에서 한 단으로 배치한다. 위아래를 흐리게 처리하고, 선택·클릭·스크린 리더 읽기에서는 제외한다.
- 본문 속 이름 두 곳과 장소 두 곳만 옅게 강조한다. 설정을 검토하는 구절 한 곳에는 가는 물결 밑줄을 쓴다. 강조 글자는 불투명도 25%로 두고, 범례·툴팁·보조 패널을 추가하지 않는다.
- 빈 공간을 새로운 설명으로 채우지 않는다.

## 구현 (2026-10 첫 화면, 이번 재설계로 대체)

핵심 문구는 `src/content/voice.ts`에서 관리한다. 랜딩과 인증, 서재가 같은 정의를 사용한다. 첫 화면의 구현은 `src/features/landing/sections/Hero.tsx`와 `Hero.css`에 있다. 백드롭은 장식을 위해 직접 쓴 고정 문장이며 회원 원고를 사용하지 않는다. 로그인 여부에 따라 시작 버튼은 회원가입 또는 서재로 연결한다. 실사용 화면도 흰 바탕·먹색 제목·Pretendard 서체와 같은 강조색 토큰을 사용한다. 서재, 작품 홈, 원고 편집, 인물·세계관·설정 검토에 적용한다.

확인: `npm run build`, `npm run lint`. 데스크톱과 모바일의 제목·시작 버튼 배치, 본문 배경의 대비와 가로 넘침, 진입 경로를 확인한다.

### 조사 당시 선택한 방향

워크룸 프레스의 작업물 중심 구성과 Are.na의 담백한 도구 UI를 우선 참고한다. 굵은 고딕으로 브랜드와 핵심 행동을 잡고, 원고의 명조체와 대비한다. 화면의 주인공은 읽을 수 있는 한 편의 원고 예시와 그 원고에 연결된 실제 기능이다. 예시는 제작한 샘플임을 표시하며 사용자의 비공개 원고를 홍보에 쓰지 않는다.

- 먼저 흑백으로 크기·줄바꿈·정렬·여백을 결정한다. 강조색은 그다음에 역할을 정해 넣는다.
- 사진은 그 사진의 대상이 해당 작품이나 기능을 설명할 때 쓴다. 분위기를 채우기 위해 넣지 않는다.
- 시각적 중심은 한 화면에 하나. 크기를 모두 키우거나 모든 영역을 카드로 감싸지 않는다.
- 숫자·기호·주석·쪽수는 실제 탐색이나 편집 기능이 있을 때만 노출한다.
- 스크롤 효과는 정보의 이해를 돕는 경우에만 사용한다. 장면을 보기 위해 긴 거리를 스크롤하게 만들지 않는다.
- 새 문구를 넣기 전에 ‘서비스 이름을 바꿔도 그대로 성립하는 문장인가’를 확인한다. 성립한다면 더 구체적인 집필 행동이나 내용으로 바꾼다.

이 판단으로 만든 원고·인물 패널 시안은 정보 과다 피드백을 받았다. 현재는 위의 시각 원칙에 따라 첫 화면을 더 단순화했다. 보류한 브루탈리즘 브랜치는 복구하지 않는다. 현재 스타일의 실사용 화면 적용 기준은 아래와 같다.

## 실사용 화면

- 공통 색상·서체·간격은 `src/styles/tokens.css`에서 관리한다. 기존 `itda` 토큰 이름은 호환을 위해 유지한다.
- 랜딩·제목·메뉴·원고·시각화에 Pretendard Variable 하나를 사용한다. 2026-10-29 단일 서체 비교 후 선택했으며, 크기·굵기·행간으로 위계를 구분한다. 실제 본문은 충분한 대비를 유지하며, 랜딩의 흐린 장식 본문을 편집 화면에 반복하지 않는다.
- 흰 바탕 `#ffffff`, 본문 `#171717`, 보조 문구 `#70706b`. 인물은 `--prolog-highlight-character`, 문장 선택·설정은 `--prolog-highlight-setting`, 검토 근거는 `--prolog-highlight-review`로 구분한다.
- 서재는 실제 작품 제목·소개·원고 수·수정 시각을 보여 주는 목록이다. 필터·정렬·더 보기를 유지한다.
- 작품 홈은 마지막 장으로 이어 쓰기와 남은 설정 검토를 우선한다. 열 수 없는 기능과 중복 지표는 앞에 노출하지 않는다.
- 편집기는 실제 원고를 Pretendard와 넉넉한 행간으로 보여 준다. 문장 선택, 질문, 자동 저장, 장 전환, 편집 이력과 보기 전용 권한은 기존 동작을 유지한다.
- 강조색은 선택한 인물·문장·검토 근거 등 실제 상태에만 쓴다. 편집 중인 원고에 임의의 인물 표시나 분석 결과를 삽입하지 않는다.
- 사이드바에는 접근 가능한 메뉴를 직접 표시한다. 모바일에서는 접고 펼칠 수 있는 메뉴를 사용하며, 이동하면 닫힌다.
